# T10 增量建模验收

在原持久化库 `data/semantic-owl-runtime/database.mv.db` 上建立独立 `T10 资料增量验收` 工作区，未清库。`fixture.json` 为合成资料与记录标识，不包含认证信息。

复跑顺序：

1. 运行 `prepare.py` 建立独立本体、资料、来源绑定、已发布版本及已确认事实。
2. 运行实例目前没有编辑 raw 原文的 API。停服并备份后，使用 `ChangeFixtureSource.java` 对 fixture 中唯一 raw ID、KB、旧文本、合成标题做条件更新；影响行数必须为 1。数据库 URL 必须 IFEXISTS，服务运行时不可离线更新。
3. 启动 `scripts/semantic-owl-runtime/start.sh` 和 `start-ui.sh`（enterprise）。在 UI 选择 fixture 对应工作区。
4. 版本页：检查资料变化 → 查看待确认事项 → 重新建模。确认进入带 taskId 的编辑页、仅一条受影响规则、新旧资料分别可读。
5. 运行 `prepare_proposal.py` 注入确定性的业务建议，UI 刷新建议、查看依据、确认本批建议。此步骤不冒充真实 LLM 效果验收。
6. 知识工作台：来源变化复核 → 扫描来源变化 → 准备事实修订；属性值改 381，引用“设备A额定电压381V。”，失焦后检查回显，提交修订申请。
7. 变更申请：核对业务结论、时间和修订依据，填写理由后确认。刷新后查看历史与新证据。
8. 执行 `readback.py --replay`；服务正常停启后再执行 `readback.py`。

浏览器截图覆盖 1440 / 390 CSS 像素；窄屏检查文档无横向溢出。`coverage.md` 记录控件与证据。

范围：新增定义/复杂类型编辑仍走原建模流程；T10 增量建议仅修改受影响规则。未知时间保留 UNKNOWN。来源复核决定与事实修订审核是不同记录，提交修订不自动关闭来源复核。真实模型自然语言生成、生产 MySQL 并发和全产品容量测试留在 T12。
