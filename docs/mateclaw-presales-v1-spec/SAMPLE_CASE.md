# 虚构演示案例：海岑精工 MES 两产线试点

本案例中的企业、产品和数值均为本规格设计的虚构测试数据，不代表真实客户需求、产品能力或实际项目承诺。

## 输入一：客户调研纪要草稿

客户计划先选择机加工一线和装配二线开展试点。目前使用纸质工单；希望跟踪工单进度，登记工序报工，将投料批次与产出批次关联，并登记不合格品处置。现有 ERP 由客户信息部维护，接口文档还没有提供。客户尚未确认预算和上线日期。有人提出以后可以探索预测性维护，但客户尚未将它纳入一期范围。

该纪要还没有客户签字确认。测试导入时应标记内部纪要/待客户核对，不直接评为客户已确认正式材料。

## 输入二：内部销售备注

估计全厂将来可能覆盖六条产线；一期可能需要给领导做一份方案汇报。销售希望方案体现未来扩展路径，但不能把六条线当作本期已确认范围。

## 输入三：虚构产品手册“HC-MOM v1.0”

本版支持工单状态查询、工序报工、批次登记、基础不合格记录；ERP 适配需要获得接口清单后评估。设备预测维护不属于本版已验证能力。移动扫码端需要配置条码编码和登录角色。成本核算未在本演示资料中说明。

## 输入四：演示案例库

案例 A：另一家虚构零部件企业实施了批次追踪。只能作为流程设计参考，不代表当前项目会实现同样收益。客户名称在对外材料中必须匿名化。没有提供可核验的收益百分比。

## 预期 Context

Goal：试点生产透明化和批次可追踪。
Process：工单下发、投料、报工、检验/处置。
Pain：纸质记录分散，进度和批次关联不方便。
Need：工单跟踪、报工、投产批次关联、不合格记录。
Constraint：一期优先两条线；ERP 接口未定。
Unknown：预算、上线日期、ERP 接口、验收阈值、终端网络、数据量。
Assumption：方案草稿可按“两条线试点，预留扩展”组织，但须标记内部工作假设/待客户确认。

## 预期澄清

谁确认一期范围？两条产线各有哪些工序和人员角色？条码编码由谁负责？ERP 提供哪些接口和主数据？上线窗口与停机限制是什么？如何验证批次关联完整性？设备和网络条件如何？

## 预期 Fit-Gap

工单跟踪 FIT；工序报工 FIT；批次登记 FIT（更复杂追溯规则另核实）；移动扫码 CONFIG；ERP 集成 UNKNOWN/待接口评估；预测维护 GAP 或本期排除且明确待后续研究；成本核算 UNKNOWN。

不得强制逐字匹配上述标签，评估语义和证据是否一致；尤其不能把“未说明”判为产品肯定支持或肯定不支持。

## 演示脚本

先导入未确认纪要，生成候选和澄清。负责人可批准有条件的内部 G1，但 UI 不显示“客户已确认”。用单独、明确标注为模拟客户答复的资料确认两条线范围，再更新事实和基线。生成方案骨架与初稿，运行独立评审，检查 ERP 依赖与预测维护边界，处理问题，渲染候选，人工 G2 后导出。

再追加一份模拟材料“增加第三条线”，验证产生新需求修订与影响提醒，旧方案和发布包不被覆写。撤销一个案例库访问权限，验证新输出不继续引用该案例原文。
