# MateClaw 售前解决方案工作台 V1.0｜实施规格

状态：待实施设计。下文新增的类名、对象名、路由、能力名和配置键均为**提议契约**，不是现有功能声明。
代码基线：`chrisopal/mateclaw` / `codex/enterprise-semantic-core` / `d45d4abb64b46f248550e713ff77633f7c362bd6`。
证据与阅读边界见 SOURCES.md。

## 1. 目标与边界

### 1.1 用户价值

用户进入一个售前项目，不必每轮重新说明客户、范围、材料、当前方案和待办。系统组织这些上下文，协助理解需求、匹配能力、编制方案、核对出处和评审风险，并保存可追溯的版本。

首版完成一个真实可用的售前闭环，而不是全部企业业务模块、通用低代码平台或多智能体市场。

### 1.2 本轮包括

- 轻量售前项目档案及客户/商机引用，可独立创建，不依赖 CRM。
- 原始材料绑定、解析状态、来源版本和证据浏览。
- Context 卡、需求候选、澄清项、冲突、人工需求基线。
- 产品能力与案例检索、Fit-Gap 矩阵。
- 结构化解决方案、按章节编辑、版本对比、需求响应关系。
- 独立方案评审、整改闭环、客户版发布确认。
- 方案 Markdown、可编辑 Word、可编辑 PPT 的模板化输出，以及证据附录和内部交接包。
- 一名主助手、一个权限更小的独立评审任务；8 个可组合 Skill。

“PPT 输出”在 V1 指可编辑文字/表格/基础架构块的企业模板，不要求每页自动生成图片、复杂动画或完全自动视觉设计。PPT 页稿先作为结构化中间产物，但仅有页稿不能宣称最终 PPTX 导出已完成。

### 1.3 明确不做

不实现投标管理、合同审核/签署、项目 WBS/工时报工、CRM 双向同步、完整报价与财务测算、外部自动发送、动态 JAR 热插拔、微服务拆分、企业总图推理平台或通用流程设计器。价值部分允许定义 KPI、计算方式和假设；不捏造 ROI、单价、客户承诺或产品能力。

## 2. 第一条业务闭环

1. 创建售前项目，填写客户、行业、目标、负责人；绑定或创建项目 Wiki。
2. 上传/绑定调研材料、客户需求、沟通纪要；补充授权产品知识库和案例库。
3. AI 生成 Context 卡、需求候选、待澄清问题；每项保留来源或标明判断/假设。
4. 人工修订并走现有语义审核；形成 G1 需求基线。
5. 基于固定需求基线，检索指定版本产品能力和案例，建立 Fit-Gap 与范围策略。
6. 先审方案骨架，再按章节生成可编辑方案、实施路线、价值指标与风险说明。
7. 运行独立评审，处理阻断项，形成受控发布候选。
8. 人工通过 G2，发布精确版本的客户成果；同时保留内部来源与交接记录。

允许反复澄清和重编方案。阶段是进度投影，不强迫所有人严格按一次性线性流程操作。没有 G1 时可生成带显著“需求未确认”标记的 provisional draft；不可称正式基线方案。

## 3. 用户界面

新增一级入口“售前工作台”。沿用现有 Enterprise/Classic 布局、设计 Token、国际化与导航规则，白底、蓝色主色、企业级表格和正常密度。不要另造一个孤立站点。

### 3.1 项目列表

显示项目名、客户、负责人、当前阶段、最近方案版本、待澄清数量、最近活动和下一步。支持搜索、负责人/阶段筛选、分页、创建及归档。只统计当前用户实际可访问内容，不输出隐藏项目数量。

### 3.2 项目详情六个页签

| 页签 | 主体内容 | 业务/AI 操作 |
|---|---|---|
| 项目概览 | 基本信息、Context 卡、阶段、未决事项 | 更新档案、生成/刷新项目理解 |
| 资料与证据 | 项目资料、产品库、案例库、解析/快照状态 | 添加来源、重试解析、查看原文、撤回 |
| 需求与澄清 | 需求矩阵、来源、性质、优先级、负责人、澄清 | 提取需求、处理候选、确认基线 |
| 能力与案例 | Fit-Gap、产品版本、能力依据、案例适用性 | 匹配能力、检索案例、确认范围策略 |
| 方案设计 | 目录、章节、架构说明、实施路线、响应矩阵 | 生成骨架、按章节生成、编辑、比较版本 |
| 评审与成果 | 评审问题、整改、发布包、Word/PPT、交接包 | 独立评审、申请发布、批准、导出 |

证据侧栏应从需求、能力匹配、评审问题或方案章节打开；展示原文位置、快照、来源状态和引用链。AI 面板是辅助入口，不挤占主工作区，也不是唯一操作路径。

### 3.3 必须呈现的状态

空数据、加载失败、模型未配置、解析不支持、来源无权限、资料更新、任务失败/取消/恢复、未保存编辑、并发冲突、输出截断、基线已过期、草稿/已发布。禁止用演示数据填充异常状态。

## 4. 业务对象与权威边界

### 4.1 首版对象

| 对象 | 内容与边界 |
|---|---|
| PresalesCase | workspaceId、engagementId、客户/外部商机引用、负责人、阶段、记录版本；不当作 CRM 全量镜像 |
| MaterialBinding | 项目绑定哪些来源及其角色：项目资料/产品/案例；引用既有 Wiki 与原始来源，不重复建解析系统 |
| ContextCardRevision | Goal、Process、Pain、Need、Constraint、Evidence、Unknown、Assumption；每个条目有来源性质 |
| RequirementWorkItem | 业务跟踪身份、负责人、优先级、响应状态；已确认内容引用 Statement 精确修订 |
| Clarification | 问题、影响、阻断级别、负责人、答复来源、处理状态；答复不是自动接受的事实 |
| RequirementBaseline | 不可变的需求/Statement 修订引用、假设、未决项、G1 决策 |
| FitGapRevision | 需求修订→能力及版本、证据、匹配类型、缺口、策略、待确认；只是评估，不自动形成客户承诺 |
| SolutionRevision | 基线引用、章节模型、响应矩阵、依赖与范围、版本/摘要、生成任务与手工修改 |
| ReviewReport | 目标方案/发布包版本、问题、证据、严重级别、整改及复核；不会批准自己的目标 |
| ReleasePackage | 最终候选成果清单、文件哈希、模板与基线引用、G2、访问政策；批准后冻结 |

复用既有任务、审批、附件与审计能力，先验证契约和权限是否足够，不因存在同名页面就假定已经可用。

### 4.2 三种内容必须分开

- **业务运营记录**：负责人、阶段、跟进时间等，售前服务为权威维护方。
- **证据支持的陈述**：通过既有语义候选、审核和 Statement 修订维护。
- **判断/假设/设计建议**：明确来源性质、提出人、影响和待确认状态，不能自动成为“客户要求”。

AI 需求文本初次可以作为候选存在；一旦确认为事实支持的需求，正式文本必须引用治理后的修订，不允许再维护一份可独立编辑的“已确认文本”。编辑正式需求意味着提出新修订并重新确认，不覆盖旧基线。

`Statement ACCEPTED` 表示通过系统事实治理，不天然等于“客户签字确认”；G1 表示内部工作基线认可，也不等于客户已经确认。另存 `customerConfirmationStatus` 和对应客户来源，禁止三个状态混用。

### 4.3 证据分级

A：可追溯的客户正式或已确认资料；B：内部纪要、产品资料等需核对其适用范围；C：未经核实的外部/内部信息。评级是本项目的使用判断，不是模型置信度，也不会自动授予发布权限。

每个条目还需独立记录 `originKind`（客户来源、产品来源、内部判断、假设、AI 建议）和审核状态；高等级来源不能证明其没有表达的内容。

### 4.4 阶段与状态

项目阶段建议：INIT → UNDERSTANDING → BASELINED → DESIGNING → REVIEWING → RELEASED；允许退回并保留历史，ARCHIVED 为另一个生命周期标记。

方案版本：DRAFT → IN_REVIEW → REVIEWED；发布使用独立 ReleasePackage 的 DRAFT → AWAITING_APPROVAL → APPROVED → PUBLISHED。审批/任务成功都不能替代实际发布状态。

所有修改携带预期版本；旧页面提交冲突返回明确冲突信息，不悄悄覆盖。ID 以字符串在前端/API 传输，继续执行仓库精度检查。

## 5. 两个人工确认门

### G1：需求基线

必须核对原子需求、证据、范围内/外、冲突、假设、关键未知和负责人。现有语义接受流程须先完成；新业务角色不能绕过原权限。

阻断性矛盾或会改变方案主干的未知不能被无声忽略。必要时允许“带条件的内部设计基线”，但必须列出批准的假设、适用条件、失效条件和责任人，不能标成“客户全部已确认”。

G1 绑定需求工作项版本、Statement 修订、来源快照、本体版本和审批人。新修订另建基线，旧基线仍用于解释历史方案。

### G2：客户输出

须完成独立评审和整改；没有未解决的阻断项；确认产品能力、范围、工期、价值数字、引用权限和输出用途。允许业务负责人接受某些明确列示的非阻断风险并写理由，但不允许审批不存在的证据或绕过访问权限。

先渲染并保存受限的发布候选文件及哈希，再审批该 ReleasePackage。通过 G2 后发布同一组字节，不重新渲染出未审核内容。待审预览 UI 标注“未批准”；未批准的可下载稿件只能走单独的水印草稿导出。

新方案修订、新模板导致内容/文件变化、新渲染产物均不能继承旧批准。审批历史保留；批准范围为具体版本和用途，不是对“该项目”永久放行。

正式发布只产生系统内成果和可下载文件，不自动发送给客户，不签约、不承诺报价。

## 6. 方案模型与输出

### 6.1 默认章节

项目背景与目标；现状流程与痛点；需求与范围；总体业务/应用/数据/集成设计；核心场景及产品能力；部署与数据安全；实施阶段与责任；价值指标与测算依据；依赖/假设/风险；验收建议与后续工作。

章节可以组合，目录先确认再扩写。每章保留 requirementRefs、capabilityRefs、evidenceRefs、assumptions、authorKind 和 revision。客户不需要看见的内部来源与评论，放在受限内部附录而不是无意带入客户文件。

### 6.2 Fit-Gap

枚举：FIT、CONFIG、EXTEND、PARTNER、GAP、UNKNOWN。

FIT 必须有对应产品版本和能力证据；CONFIG/EXTEND/PARTNER 须描述依赖、验证状态和责任方。没有证据时为 UNKNOWN，不是 FIT。案例相似不证明本产品可交付，也不证明相同收益。

### 6.3 覆盖矩阵

`需求基线条目 → 匹配结论 → 方案章节 → 证据 → 剩余缺口/处置`

覆盖率由结构化引用计算并声明分母：纳入本次范围的基线条目数。未处理、部分响应、排除和条件响应分别显示；零分母显示“不适用”，不得显示 100%。“章节提到”与“具备可交付能力”分开计算。

### 6.4 成果

需求分析包、方案骨架、方案 Markdown、Word、PPT、独立评审报告、内部版本化交接包。Word/PPT 必须可编辑；质量测试检查文字/表格溢出、乱码、页眉页脚、标题层次、引用和分页/幻灯片布局。

客户 PPT 先产生逐页标题/目标/结论/正文/布局 brief，再调用确定性模板渲染。不得把存在的前端 DOCX 预览库等同于后端导出能力；实施前查明实际导出路径与依赖。

## 7. Context 与业务接入

### 7.1 三层分工

1. PresalesContextProvider：从授权业务记录读取目标项目、当前任务、需求基线和方案版本。
2. SemanticContextService：提供版本化本体、可信事实、证据和明确标注的推理来源。[R2]
3. Wiki/产品/案例检索：按 MaterialBinding、调用者、Agent 和任务范围读取，保留版本与来源。

组装结果包含任务、actor、agent、工作区、项目、版本清单、基线、事实、假设、未决、覆盖情况、允许动作、Skill/模板版本或摘要。任务开始固定输入，后续读取和发布再次检查权限、来源状态和版本是否变化。

不得把永久保存的摘要当作来源替代品；不得把某一个 Semantic Context 的 traceId 误当作完整的持久业务任务快照。为本次任务保存引用清单和必要的受限内容摘要，用于审计，不承诺模型输出可逐字复现。

### 7.2 时间与完整性

已有语义 Context 的时间过滤可能排除 UNKNOWN 有效时间的事实。[R2] 对确实未知的时间保留未知，不用导入时间伪造业务有效时间；必要时在单独的 unverified/unknown 区列示并由人工澄清。

处理 Context 截断、缺失、撤回和权限拒绝。关键依据未获取时可输出部分草稿，不得通过正式质量门。分页过程中版本变化应重新构建或报 stale，不拼接不同版本冒充一致快照。

### 7.3 本轮不重构全部语义来源

当前 SupportEvaluator 与查询来源判断主要接受 WIKI_RAW。[R3] 本轮采取：

- 客户材料、人工纪要/答复和产品证据继续通过真实 Wiki 原始资料与已有证据流程进入语义层。
- 售前负责人/阶段等结构化运营字段直接通过受控业务 Context 读取，标明为 operational_record，不伪装成语义 ACCEPTED 事实。
- 预留通用 SourceRef/VersionRef，但不在本轮将全平台来源治理重写成新框架。
- 确实需要把结构化字段变成正式语义事实时，另列来源适配变更，覆盖导入、证据、支持性、撤回与查询全过程；禁止只新增 sourceKind 枚举就宣称完成。

### 7.4 动作契约

查询类：get_case_context、list_requirements、get_evidence、search_capabilities、search_cases。
草稿类：propose_requirement_candidates、create_clarifications、create_fitgap_draft、create_solution_draft、create_review_report。
人工作业：approve_requirement_baseline、approve_release、publish_release。

这些是拟新增业务能力名，必须映射到实际 MateClaw 工具注册机制。最后三项不放入模型可自行调用的工具清单；由经过鉴权的人工动作触发。模型返回一个 approval=true 字段不产生审批。

服务端从认证/任务绑定解析 actor、workspace、agent、case，不接受模型参数作为授权依据。动作有 operationId 和 expectedVersion，所有写入做参数校验、并发控制与审计。无原始 SQL 工具、无任意 URL 写入、无自动外发。

## 8. 权限与安全

### 8.1 不另建身份系统

当前语义访问沿用 workspace 的 owner/admin/member/viewer，并有现有系统管理员路径。[R4] 本轮复用，不将旧 PI 规格的 owner/editor/viewer 直接当作现有枚举。业务 owner 是责任字段，不自动变成 workspace admin。

G1/G2 由具备显式业务批准权限的人操作，并满足关联语义动作的既有权限。主助手可提草稿，独立评审可读和写评审结果，但不能确认事实、通过 G1/G2 或发布成果。

### 8.2 真实隔离边界

首版默认沿用现有 Workspace 安全边界；同一 Workspace 内哪些项目/知识库可被哪些人访问，必须按实际后端授权声明，不虚称已有商机级 ACL。项目材料绑定用于本次任务范围选择，不自动成为整个系统的安全隔离机制。

如本轮声称支持同工作区私有项目，必须同时覆盖业务 API、Wiki 原始资料、语义 API、工具调用、缓存、搜索、日志、附件与导出，任何原有入口都不得旁路；否则不开放“私有项目”选项，敏感隔离使用不同工作区。

即使用户有权访问两个项目，AI 在项目 A 执行任务也不得默认检索 B；通过服务端任务允许来源列表控制。确需跨项目复用案例时，显式选用已经授权和脱敏的共享案例库。

### 8.3 外部内容安全

客户文件、检索结果和模型输出均作为不可信数据，不作为系统指令。Prompt 分区、最小工具权限、服务端校验和高风险人工确认须同时实施；不能仅靠一句“不要越权”。[W1]

预览内容做 HTML/Markdown 安全处理，禁止外部图片/链接自动带出上下文；模板/工具不执行客户文档中嵌入的代码或操作指令。凭证不进前端和日志。

### 8.4 来源变化

来源更新后保留旧快照用于解释历史，并标记相关任务/方案需要复核。撤权后新的上下文、导出、发布与成果访问重新检查，不凭旧快照绕过权限；历史审计材料只对授权审计角色开放。不声称能收回已由用户合法下载的外部文件。

## 9. 为后续模块保留四个接口

1. **业务档案标识**：轻量 engagementId + ObjectRef；先由售前创建，不做全套档案中心。
2. **成果版本引用**：ArtifactRef、VersionRef、ContentDigest、DecisionRef；避免只传文件名/latest。
3. **ContextProvider**：按模块提供受控数据，售前先实现一个；不开发泛化可视化装配器。
4. **HandoffPackage**：发布时生成内部交接清单，保存需求/方案版本、范围、缺口、风险、未决项与权限引用。

本轮交接包只是受控文件/记录，不自动创建投标、合同或交付项目。后续模块接收时重新授权并显式确认接收；未来再加接收状态机和跨模块事件可靠交付。

不因“以后需要”就先做六个空模块、复杂插件生命周期和多套注册中心。

## 10. 工程组织建议

```text

mateclaw-ui/src/features/presales/

  api/
  pages/
  components/
  shared/
```

使用模块内包与原有部署；不新增独立数据库或另一套 Agent Runtime。公共 ObjectRef/VersionRef 等可以少量独立类型实现，待第二个业务模块真正复用后再抽成模块。

拟新增功能开关 `mateclaw.presales.enabled`，默认关闭。完整售前语义流程还要求原 `mateclaw.semantic.enabled=true`。关闭语义功能时界面明确能力不可用，阻止 G1/G2/发布，不静默切换成无证据模式；可按授权保留历史只读。关闭售前不删除历史数据。

数据库迁移沿用仓库惯例，新增表优先 `mate_presales_*`。已有 Wiki、语义、审批表只能通过其服务契约调用；必要扩展附 ADR 和回归测试。读配置不能显示不存在的业务能力。
